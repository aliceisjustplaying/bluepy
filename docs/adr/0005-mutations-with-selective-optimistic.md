# ADR-0005: Mutations use TanStack Query `useMutation` with selective optimistic updates

Every write in `src/data/*.ts` (`createPost`, `deletePost`, `likePost`, `repostPost`, `followAccount`, `muteAccount`, `blockAccount`, `bookmarkPost`, `markNotificationsRead`, `editProfile`, etc.) is exposed as a TanStack Query `useMutation` hook in the same module that owns the corresponding read hooks. Mutation routing follows ADR-0004's mode model: repo writes use `pds-repo-direct`; authenticated `app.bsky.*` mutations (preferences, mutes, blocks, notification-seen, etc.) use `authenticated-active-appview-via-pds`.

**Optimistic updates** are used for engagement actions where the cached object change is cheap to model and roll back: `likePost`/`unlikePost`, `repostPost`/`unrepostPost`, `followAccount`/`unfollowAccount`, `bookmarkPost`/`unbookmarkPost`, `muteAccount`/`unmuteAccount`, `blockAccount`/`unblockAccount`. These mutations patch the canonical cache entry (`keys.post(scope, uri)` or `keys.profileByDid(scope, did)` — see ADR-0016) in `onMutate`, restore the snapshot in `onError`, and revalidate in `onSettled`. Because all views read the canonical entry, a single `setQueryData` reaches every subscriber without per-query fan-out. Complex writes (compose, edit-profile, blob-upload-then-attach, mark-notifications-read) are wait-and-invalidate — they show honest pending state and do not pretend.

**Cross-scope same-viewer patching.** Engagement-mutation `onMutate` patches the current viewer scope AND every other cached viewer scope under the same `viewerDid` (different `appviewKey` or `labelersHash`) — see ADR-0016. This prevents stale-engagement bugs when a user switches AppViews or labeler sets and revisits a previously-cached scope. The cross-scope step is a same-account correctness fix; entries under a different `viewerDid` are not touched.

**Invalidation breadth.** Writes that affect feed visibility (`createPost`, `deletePost`) invalidate broadly across list keys in the current viewer scope (every `keys.timeline(scope)`, `keys.feed(scope, ...)`, `keys.profileFeed(scope, did)`, and any `keys.thread(scope, ...)` that could contain the post). Engagement writes touch the canonical post/profile entry only; list keys hold URI references (ADR-0016) and need no patching.

The agent porting code does not invent which writes get optimistic treatment — the list above is exhaustive; everything else is wait-and-invalidate.
